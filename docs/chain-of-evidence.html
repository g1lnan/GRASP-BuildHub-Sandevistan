Chain of Evidence

GRASP scores how well a student understands their own coursework. This is the case for why that score isn't a guess: what gets verified at every hop between a submission and a number, the rubric behind it, and the benchmark plan built to test whether it's actually right.

Draft 1 15 Aug 2026 Grounded in PRD.md v1.0 · DESIGN.md v1.0 Prepared for the judging panel
I

The question a judge actually asks

Ask five words about any AI grading tool: how do you know it's right? "The model is very capable" is not an answer — it's a shrug wearing a suit.

GRASP's answer is structural, not rhetorical. Every number the product shows traces back through a chain of checks, and at several links in that chain, an ungrounded output is rejected before it's ever stored — not flagged, not down-weighted, rejected. Section II walks that chain link by link, with the file that enforces each one.

A well-engineered chain that doesn't predict what a human examiner would say is still a wrong product. So Section V is not a victory lap — it's the benchmark plan that puts a number on whether the chain works, against a named baseline, with a named gate it has to clear.

II

The grounding chain

Seven hops from a student's essay to a number a lecturer can act on. At four of them, something concrete gets checked — and can fail.

  • A score with no citation is treated as a bug, not a style note. citationsMatchTranscripts() checks every cited quote against the literal text of the transcript turn it names before a score is allowed to persist — a paraphrased or invented citation fails the check and the score is never stored.

    lib/domain/scoring.ts

  • Confidence is computed, not requested. confidenceInterval() derives its margin from session completeness, probe coverage, and transcription fidelity — never from the model's own stated certainty, which is exactly the number a black-box grader would hand you instead.

    lib/domain/scoring.ts

  • A probe only survives selection if it can't be answered blind. evals/fragility sends every candidate question to a frontier model with no submission attached; a probe pool fails the gate the moment more than 25% of its questions turn out to be generic exam questions in disguise.

    lib/domain/fragility.ts · evals/fragility
III

The rubric, structured

Five dimensions, one plain-language question each, weighted by how much it separates understanding from memorised polish. This is the default barem every session starts from — configurable per assignment, but the number the calibration study is run against.

V

The benchmark plan

Two questions, and answering only one of them is how bad AI-grading products get built: which model, and compared to what ground truth. Below is GRASP's answer to both, plus the harnesses already wired to run it.

Which model

Three candidates sit on the routing table today, priced per call in lib/usage/pricing.ts so the comparison is measured, not argued.

CandidateRole todayInput $ / 1M tokStatus
Groq — gpt-oss-120b Live prototype adapter for claim graph, probes, and final score $0.15 wired now
Claude Sonnet 5 Cost/quality reference point, PRD Q1 $2.00 calibration candidate
Claude Opus 4.8 Quality ceiling — DESIGN §6.2 default for reasoning-critical paths $5.00 calibration candidate

Modelled full-session cost from DESIGN §8: ≈4,060 ₫ on Sonnet-tier, ≈7,600 ₫ on Opus-tier — both explicitly "modelled, not measured" until instrumented at scale. The Groq figure isn't modelled end-to-end yet; closing that gap is step one of the protocol below.

Compared to whom

Ground truth is blind lecturer scoring — never the model marking its own homework. Wherever a session has two independent lecturer scorings, GRASP also computes Cohen's κ between them first: if two examiners don't agree with each other, a high correlation against either one proves nothing about the model. κ is the ceiling; r is judged against that ceiling, not against 1.0.

A second, different comparison runs in parallel: probes are benchmarked against a blind frontier model with no submission attached, to test whether the questions are fair — a separate claim from whether the scores are accurate.

Protocol

  1. Freeze prompt versions for the run (cg-v3, pg-v1, score-v2) so any score difference is attributable to the model candidate, not a moving prompt.
  2. Run the identical session set through all three model candidates — same submissions, same probes where feasible, same time cap.
  3. Collect ≥2 independent blind lecturer scorings per session, scored without visibility into the model's output.
  4. Compute per-dimension and composite r, κ, MAE, and bias per candidate, plus measured cost/session in VND.
  5. Resolve PRD Q1 on the joint cost-vs-r frontier — not cost alone, and not correlation alone.
  6. Re-run the 20-session golden set (pnpm eval:golden) before every subsequent release as a standing regression gate.
VI

Proof of multiple technologies

Not one model call wrapped in a UI — seven distinct, independently testable mechanisms, each with its own file and its own unit tests.

Schema-validated structured output

Every LLM call is constrained by a Zod schema shared between the API boundary and the model's output contract — no hand-parsed JSON, no silent shape drift.

lib/ai/*-schemas.ts

Citation-verification engine

A deterministic substring check that runs on every score before persistence — a rationale that quotes something the student never said is a rejected write, not a lower confidence.

lib/domain/scoring.ts

Adversarial fragility harness

A second, independent model attempts every candidate probe blind. Fragility is measured, not asserted, before a probe is allowed near a student.

lib/domain/fragility.ts · evals/fragility

Coverage-constrained selection

Probe selection is a small combinatorial optimiser, not top-N sorting — it guarantees breadth across claim nodes and Bloom levels before it optimises for fragility.

lib/domain/probe-selection.ts

Statistics engine

Hand-implemented, unit-tested Pearson correlation and Cohen's κ — the calibration study doesn't depend on a spreadsheet macro.

lib/domain/calibration.ts

Vietnamese ASR with confidence propagation

A swappable ASR provider interface; transcription confidence flows all the way into the score's confidence interval rather than being discarded after transcription.

lib/asr/*

Per-call cost instrumentation

Every model and ASR call writes a priced usage event across two providers and three currencies of pricing, converted to VND at a configurable FX rate.

lib/usage/pricing.ts · lib/usage/record.ts

Prompt-version attribution

Every prompt module carries a version constant persisted with the row it produced — a score change is always traceable to a specific prompt edit.

lib/ai/prompts/*
VII

Proposed: the teacher's answer key as a second input

Everything in Sections II and IV grounds the score against the student's own transcript — internal consistency. It says nothing about whether what the student explained is what the assignment actually intended. A second, independent input closes that gap.

Proposed — not yet built

The gap today

A confident, well-organised, but conceptually wrong explanation can currently pass through untouched — nothing in the pipeline compares a claim to what the lecturer actually expected, because the only reference material the system ever sees is the student's own submission.

The proposal

Let a lecturer optionally attach a reference answer key or model solution per assignment, at the same configuration step as FR-104, through the same ingest path already built for FR-201 (.docx / .pdf / text).

Pipeline change

Run the existing Claim Graph extraction on the reference document — the same model call, the same schema, tagged canonical: true. Add one alignment stage that matches each student claim node to its nearest reference claim node and produces a per-assignment coverage score, plus the list of reference concepts the student's graph never touched.

reference_answer_keys { assignment_id, source, extracted_text, claim_graph_id } claim_alignments { student_claim_id, reference_claim_id, similarity, covered: boolean }

A seventh probe type

reference_gap — a probe that specifically targets a concept present in the reference key but weak or absent in the student's own graph. This is fragile in a new way: answering it requires knowing both what the assignment expected and whether the student actually addressed it — general knowledge alone doesn't help.

What doesn't change

D1–D5 stay exactly as defined in Section III. Coverage against the reference key is a new, separately-shown piece of evidence in the bundle — never silently folded into the composite, never a sixth dimension, never a stored label. That preserves FR-405 (the 2×2 is derived, never stored as an accusation) and the entire premise of this document: no verdict without a citation attached to it.

Why this matters here

It answers the mentor's note directly — "the input might be the teacher's answer sheet" — and it's the next thing a skeptical judge would ask for after reading Section II: you've shown me the score is internally consistent; now show me it's externally correct. This is that second axis.

VIII

What we don't claim yet

A document arguing for grounded trust forfeits the argument the moment it overclaims. Four open items, stated plainly.

  • G1 has not been run. Composite r > 0.7 across 300 sessions is the gate, not a result — no pilot data exists yet to compute it against.
  • The cost model is modelled, not measured. The 4,060 ₫ / 7,600 ₫ figures in DESIGN §8 are estimates pending real usage_events aggregation at scale.
  • The typed-vs-voice validity gap is open, not closed. The scoring prompt is instructed to ignore input mode, and typed responses correctly show full transcription reliability — but whether the two response conditions are truly comparable in practice is an unmeasured question, tracked explicitly in DESIGN §11.
  • Section VII is a design proposal. No reference-answer-key schema, alignment stage, or new probe type exists in the codebase today — it's scoped, not shipped.
